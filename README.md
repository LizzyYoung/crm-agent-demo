# CRM 内嵌式 AI Agent — 产品作品集

> 面向培训机构销售团队的 **CRM 内嵌式 AI Agent** 产品设计与效果评测记录。
> 产品负责人：**廖子渊（Lizzy）**　｜　周期：2026.09 – 2026.10　｜　v1.0 → v5.0

---

## 一句话

给一家培训机构「教育事业部」的 5 人销售团队，做一个**长在 CRM 里**的 AI 销售助理 ——
让销售每天早上 3 分钟就知道「今天该跟谁」，开口前就知道「这个客户聊过什么」。

---

## 1. 为什么做：问题有多严重

**用户**：5 名销售专员（覆盖 5 个区域）+ 1 名销售主管。**线索是他们的核心资产。**

**现状**：销售每天的工作方式是「翻页 + 靠记忆」——

| 痛点 | 实测数据 |
| --- | --- |
| 客户背景散落，接触前要重新拼一遍 | 想看一个客户的完整背景，要在「线索管理」和「沟通记录」两个页面间来回切、把 **15 条消息一条条读完再自己归纳** —— 实测 **12 个动作** |
| 聊过的没记、记了没人看 | **50 条线索里 37 条（74%）没有任何沟通记录** |
| 线索会因为人的原因掉在地上 | 6 条线索处于「未接触 / 长期未跟进」；系统备注里直接写着「**销售员请假期间未跟进**」 |
| 该跟谁全凭经验 | 没有统一的判断依据，「今天该跟谁」靠记忆 |

> 不是线索不够 —— 是**这些该跟的人，没有人兜住**。

---

## 2. 我的第一个产品判断：哪些事「不该」交给模型

上手时我先做了一件事：**把需求拆成两类，而不是把所有事都丢给模型。**

| 需求类型 | 判断 | 落地方式 |
| --- | --- | --- |
| 线索评分、字段计算 | **确定性规则** | **交给代码算，不让模型「心算」** |
| 查客户背景 / 答客户问题 / 生成月报合同 | **开放任务** | 交给模型，但**严格限定它能调用哪些工具** |
| 定时出月报 | **高确定性** | 用规则 + 定时执行，**不让 Agent 自由发挥** |

这个拆分直接决定了整个产品形态：**能力分三层**（确定性能力 / 知识与流程 / 外部服务），
以及一套**在模型动手之前就生效的权限边界**。

---

## 3. 核心设计：治理策略（读 / 写 / 删三档）

> 一条产品原则：**高风险动作不能靠提示词让模型自觉，要靠机制拦住。**

| 操作类型 | 策略 | 说明 |
| --- | --- | --- |
| **读** | 放行 | 查询类操作直接执行 |
| **写** | **弹审批卡等人确认** | 改数据必须在对话内弹出审批卡，人批准后才执行 |
| **删** | **拒绝** | 直接拒绝，不给模型任何删除路径 |

**实现上的关键转折**：一开始我打算直接用框架自带的 `excluded_tools` 做拦截 —— 读了源码才发现
**它只是"让模型看不见"，并不等于拦得住**（工具仍在注册表里）。据此把**拦截点前移到工具真正执行之前**，
做成一道统一闸门。

这套设计与主流 AI 产品 JD 里的「**安全护栏 + 人工介入**」直接对应。

## 4. 效果评测：用真实业务结果回溯，而不是自造测试集

**方法**：以 **50 条真实线索**做回溯验证，**对齐客户最终「成交 / 流失」这个真实业务结果**。

| 指标 | 实测值 |
| --- | --- |
| 80 分阈值 · 命中条数 | 22 条，**全部成交** |
| 80 分阈值 · **精确率** | **100%** |
| 80 分阈值 · **召回率** | **62.9%**（会漏掉约 1/3 的成交客户） |
| 成交组 vs 未成交组 · **区分度** | **23.0 分**（73.3 vs 50.3） |
| 安全反向测试 | **5 类场景 100% 通过**（越权读取 / 要求删除 / 未审批改数据 / 字段缺失 / 提示词注入） |
| 典型任务动作数 | **12~20 → 4~6**（逐场景实测） |

### ⚠️ 我主动把短板写进结论

**召回率只有 62.9%** —— 意味着以 80 分为线，**会漏掉约 1/3 最终成交的客户**。

具体到个案：我定位到 **2 例「高分却流失」的线索**，归因到评分规则缺失的两个维度 ——
**「决策时机」**（客户现在是不是在选型窗口期）和 **「竞品对比」**（客户是否已在比较竞品）。
这两个维度决定的是"什么时候跟"和"怎么跟"，而不是"值不值得跟"——这恰恰是纯静态画像看不出来的。

> 80 分是「**宁可漏、不可错**」的档；50 分档召回率 91.4%，但精确率掉到 76.2%。
> 阈值取舍本身就是产品决策。

## 5. 版本迭代（v1.0 → v5.0）

| 版本 | 主题 | 主要内容 |
| --- | --- | --- |
| **v1.0** | 对话与工具骨架 | 会话隔离、信息查询 Tool、三档权限拦截器、Agent 控制面板 |
| **v2.0** | 知识库与线索分析 | 线索分析 Skill（5 项固定模板）、RAG 检索与引用来源回显、知识库管理 |
| **v3.0** | 结果型（生成 + MCP） | 销售月报 HTML 生成、合同 Word 生成、MCP 外部服务接入、文档与 MCP 管理页 |
| **v4.0** | 数字员工（主动 + 评分 + 记忆） | 定时任务、线索评分（5 维 100 分规则）、长期记忆、记忆管理 |
| **v5.0** | 体验优化与安全管控 | 账号级数据权限、Token 限额与上下文用量、多模型供应商、图片 / 文件输入 |

**每个版本配独立的验收清单**（共 19 份，逐项过）。

## 6. 成本与可替换性

| 项 | 做法 |
| --- | --- |
| Token 成本 | 按账号限额，**超限在调用模型之前就拦住**（不花冤枉钱） |
| 上下文用量 | 可视化，超 80% 告警 |
| 模型可替换 | 多供应商可配置切换，**密钥在界面脱敏** —— 不让客户被单一厂商绑死 |

**实测**：一次「查客户全部背景」的模型成本约 **¥0.039**（≈30,200 tokens）。
> ⚠️ 该数字基于官方价目表的 **off-peak 单价**折算；cache hit 比例与峰谷时段分布未采集，故为量级参考而非精确值。

## 7. 技术实现

产品定义、数据模型、前后端实现与评测脚本**均由我独立完成**（AI 辅助编码）。
本项目是产品设计能力的载体，**我不把它表述为工程开发能力**。

- 前端：Next.js（CRM 15 个页面 + 内嵌 AI 助手页 + Agent 控制面板 9 个 Tab）
- Agent：Python + FastAPI + deepagents，43 个端点
- 模型：DeepSeek（对话 / 工具调用）+ SiliconFlow（bge-large-zh 向量化）
- **未做模型微调** —— 用 RAG + 提示词工程 + 规则外置达成，理由是金标数据成本与 ROI 不划算

## 8. 已知边界（主动说明）

| # | 边界 |
| --- | --- |
| 1 | **无线上用户** —— 这是产品设计与评测完整的 demo，不是已上线产品；北极星指标（跟进及时率）尚未取得 |
| 2 | **目标用户来自数据集反推，非真实客户访谈** —— 痛点数据真实可复现，但"用户访谈"这一环缺失 |
| 3 | 评测样本 50 条，**召回率 62.9%**，仍需扩大样本与补充维度 |
| 4 | 评测集（FAQ 30 条）**规模小于行业标准**，尚未扩到 200+ 条并补 corner case |
| 5 | Agent 四能力中 **「反思 / 自评」节点尚未实现** |
